# AVaaS Enterprise — Agent Validator as a Service

Multi-tenant AI Quality Engineering / AgentOps platform: it tests, evaluates,
governs, and release-gates AI agents individually and as chained multi-agent
workflows. Aligned with the included TechCon 2026 proposal and the
[Strategic Vision doc](docs/STRATEGY.md), which covers the stakeholder map,
KPIs, governance model, assumptions/constraints/risks, cost considerations,
competitive positioning, and roadmap in full.

## What is implemented

**Core validation**
- React + TypeScript + Tailwind CSS 3 dashboard, including an AgentOps KPI panel, governance/policy manager, and multi-agent workflow builder.
- FastAPI backend with tenant/user/membership/project/target/run/result mappings.
- JWT access tokens, rotating hashed refresh tokens, Argon2 passwords, RBAC, encrypted target credentials, and audit events.
- Browser-hosted agent testing using local Playwright Chromium; no Playwright API key is required.
- OpenAPI discovery and extension modes for mapped REST and transcript validation.
- Optional business requirements: the LLM may infer generic scenarios from discovery evidence, but inferred statements are never authoritative business rules.
- Ollama first with one bounded Gemini 2.5 Flash fallback call.
- Rule, safety/hallucination, and optional business/MVP evaluation with composite scores.
- Langfuse primary tracing, OpenTelemetry primary alternative, LangSmith commercial fallback, and persisted local evidence if exporters fail.
- DeepEval dependency and configuration for evaluation-extension integration.
- Baseline/candidate data model and release-gate (`PASS`/`WARN`/`FAIL`) outputs.
- SQLite local default; PostgreSQL recommended for production.

**Infrastructure & deployment**
- **PostgreSQL + Alembic**: `db.py` reads `DATABASE_URL`, so switching from the SQLite default to Postgres is config-only. `migrations/` holds an autogenerated initial migration; `alembic upgrade head` builds the schema. `AUTO_CREATE_TABLES=false` hands schema ownership to Alembic in production.
- **Docker + docker-compose**: `docker-compose.yml` runs Postgres + backend + frontend + mock-agent; `backend/Dockerfile`, `frontend/Dockerfile`, `mock-agent/Dockerfile`, and a `Makefile` are included. (The compose stack's config is complete and internally consistent; it was authored but not booted in the build sandbox — verify locally with `docker compose up --build`.)
- **Standalone mock agent** (`mock-agent/`): a runnable REST agent exercising all eight spec behaviours (normal, invalid input, multi-turn, tool call, business-rule violation, malformed response, latency, downstream state change) so the whole pipeline runs locally with no external LLM/API.
- **Async runner resilience**: bounded retry with exponential backoff on transport errors and 429/5xx, optional client-side rate limiting, and a correlation id propagated per execution — all configurable.

**Universal endpoint ingestion & evaluation depth**
- **REST/OpenAPI adapter** drives any live FastAPI or standard REST agent endpoint — configurable method, path, prompt field, response path (dotted, e.g. `data.choices.0.message.content`), headers, and encrypted auth, so no target-specific code is needed.
- **True multi-turn execution**: `multi_turn` cases carry an ordered `turns` array and are executed as a real dialogue with session continuity (session id for REST, one held page for browser); the LLM judge receives the full transcript.
- **Deterministic rule tier** (`services/rules.py`) — JSON parsing and JSON-Schema validation, internal-error/stack-trace leak detection, HTTP status checks, required/forbidden content, multi-turn completeness, and length sanity. This is the tier that catches malformed-JSON and silent-failure classes without spending a token. DeepEval is wired in as an optional metric extension.
- **Trace collection** captures tool calls, per-turn transcripts, status codes, latency, and correlation ids as evidence.
- **Tier-2 generic quality judge** (`services/deepeval_judge.py`): DeepEval when enabled and reachable, degrading to a built-in LLM rubric judge, then to skipped — never fabricating a score. Weighted into the composite via `COMPOSITE_QUALITY_WEIGHT`.
- **Downstream state verification** (`services/state_validation.py`): a case may declare a `state_check` (read-only URL + expected value/operator); AVaaS verifies the agent's claimed side effect actually landed in the downstream system, and a declared-but-violated check fails the case. Arbitrary SQL execution is deliberately not exposed.
- **Baseline vs candidate regression + release gate** (`services/regression.py`, `GET /runs/{id}/regression`): compares composite score, pass rate, hallucination rate, and risk against a baseline, and returns an explicit PASS / FAIL / BLOCKED decision — BLOCKED when a hard gate (critical governance finding, state-check failure, sub-50% pass rate) trips regardless of baseline.

**Enterprise governance & AgentOps**
- **Prompt/config version management** per target (`/targets/{id}/prompt-versions`), fully audited.
- **Policy engine** for compliance, security, PII, and responsible-AI rules (`/projects/{id}/policies`), evaluated deterministically against every response — independent of the LLM judge, so a hallucinating judge can never silence a governance violation.
- **Built-in PII detector** (email, phone, SSN-like, credit-card-like, IP, API-key-like strings) with masked findings, always on.
- **Per-run Risk Score and Release Confidence**, and a **portfolio-wide KPI dashboard** (`GET /api/v1/kpis`): release-gate pass rate, hallucination detection rate, avg risk score, regression-detection accuracy vs. baseline, test coverage, cost per validation run.
- **Multi-agent / end-to-end workflow validation** (`/projects/{id}/workflows`, `/workflows/{id}/runs`): chain several targets into one validated business process, with each step's strongest response carried forward as context for the next agent, rolled up into a single workflow release gate.
- **Audit trail** extended to cover governance actions (policy changes, run/workflow completion with gate + risk score, certificate issuance), not just CRUD.

**Requirement & Use Case Analysis Engine**
- `POST/GET /projects/{id}/analysis` (`services/analysis.py`): converts a use-case definition, business requirements, and an agent description into structured use cases, source-classified requirements (`EXPLICIT`/`DERIVED`/`INFERRED`/`UNKNOWN`), user intents, test-scenario stubs, and explicitly-flagged requirement gaps — versioned per project.
- An `EXPLICIT` claim is deterministically re-checked against the actual supplied source text and downgraded to `DERIVED` if it isn't traceable, so a tool's mere existence can never be silently promoted into an authoritative business rule.
- Test generation prefers this structured analysis when one exists, stamping `requirement_id`/`use_case_id`/`scenario_id` onto every generated case and result; `GET /runs/{id}/traceability` walks the resulting Use Case → Requirement → Test Case → Execution chain for one run.
- **Known limitation**: accepts extracted text, not an uploaded PDF binary parsed server-side — noted plainly in `docs/STRATEGY.md` rather than glossed over.

**AI Test Intelligence, Certification & Continuous Validation**
- **AI Test Intelligence** (`POST /projects/{id}/intelligence`): coverage-gap detection across case archetypes and business requirements, regression-suite recommendation ranked by flakiness/failure history/governance signal, and an **explainable** release-risk prediction where every contributing factor is returned with the score.
- **Agent Certification** (`POST /targets/{id}/certificates`, `GET /certificates/{id}/verify`): HMAC-signed, 90-day-expiring certificates binding target + prompt version + run evidence, verifiable offline so a CI/CD gate can consume them. `DENIED` certificates are issued and stored too, so refusals are auditable.
- **Production Monitoring / Continuous Validation** (`POST/GET /targets/{id}/monitor`): ingest live interactions, score them through the same deterministic tiers used at release time, and detect drift against the certified baseline (`HEALTHY` → `GOVERNANCE_FINDINGS` → `DRIFT_DETECTED` → `CRITICAL_DRIFT`).
- **Compliance Reporting** (`GET /projects/{id}/compliance-report`): one auditable export of gates, findings by category/severity, certificates, and audit trail — downloadable as JSON from the dashboard.


## Problem and objective

Agents fail silently. A prompt tweak, a RAG-index change, or a model upgrade can
turn a working agent into one that hallucinates tool arguments, emits malformed
JSON, leaks a stack trace, breaks a business rule, or quietly stops doing the
thing the business actually asked for — while still returning a fluent-looking
200 OK. AVaaS exists to make those failures visible *before* release and to keep
watching after it, with evidence a governance reviewer can audit.

## Data flow

```
Business requirement / use case / agent description
        │
        ▼  Phase 1  services/analysis.py
Structured spec: use cases, EXPLICIT|DERIVED|INFERRED|UNKNOWN requirements,
acceptance criteria, scenario stubs, requirement gaps
        │
        ▼  Phase 1  services/pipeline.py (generation)
Requirement-linked test cases (normal / edge / injection / multi-turn),
each stamped with requirement_id · use_case_id · scenario_id
        │
        ▼  Phase 2  services/adapters.py  (asyncio + httpx, bounded concurrency,
                     retry/backoff, rate limit, correlation id, multi-turn session)
Execution evidence: response, transcript, status codes, tool calls, latency, tokens
        │
        ▼  Phase 3  Tier 1 rules.py · Tier 2 deepeval_judge.py · Tier 3 pipeline judge
                     + compliance.py/pii.py governance + state_validation.py
Composite score (configurable weights) · governance findings · state verification
        │
        ▼  Phase 4  services/regression.py · certification.py · monitoring.py
Baseline comparison → PASS / FAIL / BLOCKED release decision → signed certificate
→ production drift watch
```

## The four-phase pipeline

| Phase | What it does | Code |
|---|---|---|
| 1 — Analysis & generation | Structures requirements with source discipline, then generates requirement-linked test cases | `services/analysis.py`, `services/pipeline.py` |
| 2 — Async execution | Bounded-concurrency runner with retries, backoff, rate limiting, correlation IDs, multi-turn sessions, trace collection | `services/adapters.py`, `services/observability.py` |
| 3 — Multi-tier evaluation | Tier 1 deterministic rules → Tier 2 generic quality → Tier 3 business/MVP judge, plus governance + downstream state verification | `services/rules.py`, `deepeval_judge.py`, `pipeline.py`, `compliance.py`, `state_validation.py` |
| 4 — Regression & release | Baseline vs candidate comparison, PASS/FAIL/BLOCKED gate, certification, production drift | `services/regression.py`, `certification.py`, `monitoring.py` |

## Test through the UI

1. Register an organization, tenant slug, owner email, and strong password.
2. Create a project.
3. Choose **Browser website**.
4. Enter a public agent UI URL.
5. Click **Discover agent**. AVaaS opens the page with Playwright and inspects visible inputs, content-editable controls, buttons, response regions, iframes, and browser errors.
6. If discovery succeeds, click **Validate**.
7. AVaaS generates bounded normal, edge, injection, and multi-turn cases using Ollama, with Gemini fallback.
8. Playwright enters prompts into the real website UI and captures output, latency, browser errors, adapter details and target evidence.
9. AVaaS evaluates deterministic rules, safety/hallucination, and business/MVP criteria when authoritative requirements exist.
10. Review run status, score, evidence and release gate.

Business/use-case fields are optional. When absent, AVaaS may infer generic scenarios from page discovery; those inferences do not become authoritative business rules.

## Governance, KPIs, and multi-agent workflows

1. Open the **Governance & Compliance Policies** panel and add a rule (e.g. category `responsible_ai`, pattern `guaranteed refund`). It's evaluated deterministically against every future response for that project, in addition to the LLM safety judge.
2. Run validations as usual. Any result whose response matches a policy rule, or contains detectable PII, is flagged inline with severity and shows up in that run's Risk Score.
3. Open **AgentOps Portfolio KPIs** at the top of the dashboard for tenant-wide release-gate pass rate, hallucination rate, average risk score, and total validation cost, computed from persisted run evidence.
4. Open **Multi-Agent Workflows**, name a workflow, click through two or more targets in order to chain them, and create it. Click **Run** to validate the whole chain: AVaaS executes one full validation run per step and carries the strongest response from each step forward as context for the next, then rolls the steps up into a single workflow release gate.
5. Use **History** on a workflow to see past workflow runs and their per-step gates.

## Configuring a REST / FastAPI target

Choose mode `rest` (or `openapi`) and supply an Advanced Config JSON describing the contract:

```json
{
  "path": "/chat",
  "method": "POST",
  "prompt_field": "message",
  "session_field": "session_id",
  "response_path": "data.reply",
  "headers": {"X-Env": "staging"},
  "timeout": 60
}
```

Only `path` is usually needed — `prompt_field` defaults to `message`, and without a `response_path` AVaaS tries common reply keys (`response`, `message`, `answer`, `output`, `text`, `reply`, `result`, `content`) before falling back to evaluating the whole JSON body. Credentials go in the target's `auth` field (encrypted at rest, never logged): `{"bearer": "..."}` or `{"api_key": "...", "api_key_header": "X-API-Key"}`.

`session_field` is what makes multi-turn real: AVaaS sends a stable session id across the turns of a `multi_turn` case so the agent's own memory is exercised.

The schema is owned by Alembic. `backend/app/db.py` reads `DATABASE_URL`, so the
same migrations work against SQLite and PostgreSQL.

```bash

alembic downgrade base      # tear the schema back down
alembic revision --autogenerate -m "describe change"   # after changing models
```

In development `AUTO_CREATE_TABLES=true` lets the app create tables at startup
for zero-setup runs. **Set `AUTO_CREATE_TABLES=false` in production** so Alembic
is the single source of truth.

```bash
DATABASE_URL=postgresql+asyncpg://avaas:avaas@localhost:5432/avaas
```

`tests/test_migrations.py` asserts the migration produces every table the ORM
defines, so models and migrations can't silently drift apart.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `ValidationError: N validation errors for Settings` | No `.env` present. Run `scripts/bootstrap.sh`, or `cp backend/.env.example backend/.env` and fill `JWT_SECRET` / `FIELD_ENCRYPTION_KEY`. |
| Run stays `queued`/`failed` with an LLM error | No provider reachable. Start Ollama (`ollama serve`) or set `GEMINI_API_KEY`. |
| `Input <selector> not found` on a browser target | The page is an SPA still loading, or it blocks automation. Set explicit selectors in the target's Advanced Config. |
| Target URL rejected before any request | The SSRF guard blocked a private/loopback address. Set `ALLOW_PRIVATE_TARGETS=true` for local targets like the mock agent. |
| `alembic: command not found` | The venv isn't active, or deps aren't installed: `pip install -r backend/requirements.txt`. |
| Frontend can't reach the API | Check `VITE_API_URL` in `frontend/.env` and that the origin is listed in `CORS_ORIGINS`. |
| Tests fail on a second run | Stale DB artifacts — `rm -f backend/avaas.db backend/tests/*.db`. |

## Security

- JWT access tokens plus rotating, hashed refresh tokens; Argon2 password hashing.
- Role-based access control (`owner`, `admin`, `qa`, `viewer`) on mutating routes.
- Target credentials encrypted at rest with Fernet (`FIELD_ENCRYPTION_KEY`); never logged.
- SSRF guard on every outbound target/state-check URL; private ranges blocked unless explicitly allowed.
- Correlation ID on every request; unhandled errors return a generic body and log server-side, so internals and secrets never reach a client.
- `.env` is gitignored and `.env.example` contains placeholders only.
- See `docs/SECURITY.md`.

## Multi-tenancy

Every domain table carries `tenant_id`, and **every query filters on it** — there
is no code path that reads another tenant's rows. Membership + role are resolved
per request from the JWT. `tests/test_tenant_isolation.py` and the cross-tenant
assertions in `tests/test_api_governance.py` verify that a second tenant sees an
empty list (or a 404) on every resource the first tenant created.

## Observability

Primary is Langfuse and/or OpenTelemetry; LangSmith is the commercial fallback.
Exporter failures never fail a run — evidence is always persisted locally, and
unavailable trace/tool/token data is recorded as unavailable rather than invented.

## Scalability and production deployment

- Set `AUTO_CREATE_TABLES=false` and let Alembic own the schema.
- Move to PostgreSQL via `DATABASE_URL`; the app needs no code change.
- Tune `MAX_CONCURRENCY`, `REQUEST_MAX_RETRIES`, and `REQUEST_RATE_LIMIT_PER_SEC` to the target's capacity.
- **Known limitation:** runs currently execute in FastAPI `BackgroundTasks`, so an
  in-process restart mid-run loses that run's progress (committed results survive).
  A durable worker queue (Celery/Arq) is the main production prerequisite and is
  the top near-term roadmap item in `docs/STRATEGY.md`. The service interfaces
  (`execute_run`, `execute_workflow`) are already async and queue-ready.
- Run the frontend build behind a CDN/static host; the included `frontend/Dockerfile` serves it via nginx.

## Known external-service limitations

| Service | Status in this build |
|---|---|
| Ollama | Real client; not reachable in the authoring sandbox, so live generation was exercised via stubs. Works locally once `ollama serve` runs. |
| Gemini | Real client; requires your own `GEMINI_API_KEY`. Never called without one. |
| Langfuse / OTel / LangSmith | Real exporters; disabled by default and untested against live endpoints. Failures are swallowed by design so they cannot fail a validation run. |
| DeepEval | Real integration, off by default (`USE_DEEPEVAL=false`); degrades to a built-in LLM rubric judge, then to skipped. Never fabricates a score. |
| Docker / PostgreSQL | Configuration complete and YAML-validated, but the stack was not booted during authoring. Verify with `docker compose up --build`. |
| PDF ingestion | The analysis engine accepts extracted **text**, not an uploaded PDF binary parsed server-side. |


## Website limitations

A URL alone cannot guarantee automation of every website. CAPTCHA, mandatory SSO, anti-bot systems, cross-origin iframes, canvas-only UIs, cookie overlays, and unusual multi-page workflows may require credentials, explicit selectors, recorded workflows, or transcript mode. AVaaS reports discovery limitations rather than fabricating success.

For a local/private target, `ALLOW_PRIVATE_TARGETS=false` protects against SSRF. Set it to `true` only in a controlled local environment, never on a public deployment without strict network allow-listing.

## Production checks

```powershell
cd backend
.\.venv\Scripts\Activate.ps1
python -m compileall app
python -m pytest -q
cd ..\frontend
npm run build
```

`pytest -q` runs 23 tests across five files:

- `test_tenant_isolation.py` — model-level tenant scoping.
- `test_governance.py` — PII detection, policy evaluation, risk scoring.
- `test_e2e_pipeline.py` — spins up a **real mock agent** in-process and drives it through the REST adapter: single-turn, multi-turn with session continuity, error-leak detection, JSON-Schema validation, and PII flagging on a live response.
- `test_intelligence_certification.py` — coverage gaps, regression-suite ranking, risk escalation, certificate signing/tamper-detection, and drift reporting.
- `test_api_governance.py` — full API flow with real auth, plus **cross-tenant isolation assertions** on every new endpoint.

Tests run against a throwaway SQLite file (`tests/conftest.py`) so they never touch a developer's `avaas.db`, and the SSRF guard is relaxed for tests only via the environment — never by weakening the guard itself. 31 tests pass as of this iteration; `test_analysis_engine.py` specifically exercises the EXPLICIT-claim downgrade guardrail.

For production, use PostgreSQL, migrations, RLS, OIDC/SSO, a secret manager, rate limiting, a durable worker queue, TLS, exact CORS origins, egress allow-lists, monitored trace exporters, backups, and refresh-token cleanup. Do not use FastAPI in-process background tasks across multiple replicas.
